# Jobloom 全面反思与改造优先级

日期：2026-10-12。评估基于本地版本 15e9a11、现有源码、本地脱敏汇总及官方产品资料。本轮只做研究与文档，不改业务代码，不连接真实账号，不调用岗位评估模型，不投递或发送消息。

## 结论

当前系统把找工作拆成了许多页面操作，却没有形成一个能持续推进机会的求职流程。主要问题是：候选依赖会变化的列表，技术失败被转成用户待办，所有未知条件进入同一人工池，搜索没有结果反馈，开聊之后没有完整的回复与面试管理。

首先应修复候选的流失和分流责任，再改搜索策略，再补回复、跟进、面试等功能。单纯降低 AI 分数线、加快点击或增加搜索轮数，无法解决这些问题。

## 1. 可确认的本地证据

### 1.1 待确认队列快照

| --- | ---: | --- |

| needsDetailConfirmation | 113（56.5%） | 技术/资料重读类问题占多数，不能当作用户需要判断的工作条件 |

这是一个被截断、跨任务累积的候选池，不能据此声称“所有扫描岗位中56.5%发生故障”或“本轮200个岗位全部需要人工”。

### 1.2 历史长测

data/live-delivery-long-test/report.json 中 10月7日最后一段：约31分钟，扫描计数95，AI请求7次，确认新开聊1次。1/95约1.05%，但扫描计数可能包含重读，且版本、条件与今天不同，不能当成当前唯一岗位命中率。

这份记录可以证明当时端到端产出很低；不能证明现在的原因全部相同，更不能证明平台不会限制账号。

## 2. 为什么搜索变多，命中没有跟着增加

### 2.1 来源策略是静态遍历

当前按 sources 顺序扫描；自选模式先设置最多三个官方岗位，然后分别打开该来源。它没有根据新增岗位、规则通过、最终开聊或回复收益来调整下一轮。

当前配置的来源是自选期望，目标只有一个店员/营业员。自选模式会使用配置后的来源名，keywords 并不是这一模式的实际搜索组合。继续重复一个来源，不等于扩展了有效搜索范围。

需要搜索方案：岗位方向、同义标题、技能词、城市/范围组成可解释的组合；按各方案的新增唯一候选和后续收益分配搜索时间。扩展应遵守原排除项，不偷偷放宽用户硬条件。

### 2.2 “扫描次数”不是“新找到多少岗位”

processedJobKeys 只在一轮任务内存在。详情重读会删除已处理标记，再次增加 totalScanned；重启后也没有完整的持久岗位去重台账。passedFilterCount、当天开聊数、规则决策数分别是不同口径，不构成一个严密漏斗。

真正应记录：列表呈现 → 新增唯一岗位 → 详情成功 → 硬规则保留 → 可处理候选 → 实际开聊确认 → 收到回复 → 条件确认 → 面试。每一层记录流失原因，区分本轮与当天。

### 2.3 新来源没有自适应收益判断

主循环连续六次没有新岗位后结束来源；翻页的局部变化等待约900ms。900ms不等于六轮总等待，也不能仅据源码断言每次提前结束，但结束逻辑没有把明确到底、加载缓慢、列表重排和来源重复分别呈现给用户。

搜索轮数和命中数不必线性增长，重复来源本就会收益递减。系统的责任是识别新增率下降并换合理来源，而不是用循环次数营造进度。

### 2.4 候选已经找到，却在评估后流失

delivery.service.ts:581 起，AI批次处理后先从当前列表找 freshCard；找不到就 retainDetail，进入人工池。系统明明已保存 jobHref，却依赖变化后的列表是否仍显示该岗位。

批量 AI 是合理的，但候选对象仍携带 locator，评估、浏览、休息和投递挤在同一主循环。异步评估与会变化的页面状态冲突，形成“找到→评分→找不回→人工”的流程。

正确责任：以稳定岗位身份、岗位链接和资料快照为核心；投递前根据链接重新取得详情和按钮。资料变化进入自动重新筛选，而不是默认人工复核。暂停和浏览器重开只影响浏览器句柄，不应让岗位业务状态丢失。

## 3. 为什么绝大多数工作被交给人工

### 3.1 把不同性质的未知合成了同一个 needsReview

目前人工池同时接收：列表变化、详情未就绪、资料更新、公司业务不明、工作条件没写、AI格式错误、资格资料缺失和位置不明。这些并不都是人的决策。

| 情况 | 应由系统做什么 | 什么时候才需要人 |
| --- | --- | --- |
| 列表换了/定位失败 | 按岗位链接重新读取，保留任务进度 | 自动恢复持续失败且确需用户操作 |
| 详情或公司资料变了 | 更新快照，按当前规则重新评估 | 存在真实业务歧义且无法补全 |
| AI请求失败/格式异常 | 补读同一次结果、校验、有限重试，保留待处理队列 | 请求范围或业务决策必须由用户确认 |
| 工时/双休没写 | 区分可沟通询问与投递前必须证实 | 用户尚未授权处理此类未知，或回复仍有重要矛盾 |
| 没有明确硬门槛冲突 | 按用户投递策略推进，AI作排序参考 | 岗位是否值得尝试确需主观选择 |
| 面试时间/薪资协商/承诺 | 提取事实、提醒并给建议 | 用户作最终选择和承诺 |

技术失败必须进入系统自己的恢复队列。它可以等待、重试、暂停该岗位；不能把“保存到人工池”算作自动化完成。

### 3.2 改提示词解决不了先于分数的硬出口

filter.service.ts:314 起，条件汇总发现 unknown 就 needsReview；此后才执行分数和 missingEvidenceOnly 判断。因此，即使 AI 给高分、认为简历没写不应淘汰，岗位仍会因为一个条件未写而进入人工。

用户条件目前只有 enabled 与文本，缺少“不可接受的明确冲突”“必须投递前证实”“可以先询问确认”“偏好排序”的不同决策语义。不能把所有愿望机械地解释成投递前必须出现一段原文。

此前用户授权“描述明确符合三项就可投递”，只覆盖明确符合的情形，不等于授权系统将未写的条件视为符合。要提高自动化，应一次明确未知条件的处理策略，之后让系统持续执行；不是给每个岗位再问一次，也不是静默删除条件。

### 3.3 人工池没有形成自动回流

队列存储200条，新增记录直接截断较旧记录。listEligible 主要按当前排除与地点筛查，不能自动让全部旧工作条件重算；缺少任务ID、条件版本、失败原因分类、重试进度和过期归档。

用户关闭双休后，历史待办仍展示双休。记录不是事实错误，但界面没有把历史依据与当前策略清楚区分，增加了无效人工判断。

需要版本化规则与资料；条件调整后只重算受影响候选，明确显示已重新评估、历史结论、已失效。达到容量上限应归档和提示，不能默默丢掉未完成工作。

## 4. 效率与可靠性也存在结构问题

- 脚本初筛在完整详情/部分公司核查之后才执行，许多“初筛”已经付出较高浏览成本。可在列表阶段做廉价排序和确定的去重，最终决定仍以详情为准，避免重回卡片误判。
- 公司缓存是内存缓存，默认5分钟；AI批次回投又要求 refreshCompany。是否需要刷新，应依据资料有效期、真实变化或高风险业务，不是每个岗位无差别多次刷新。
- AI评估缓存仅内存保存30分钟；任务停下或重启会失去候选与评估连续性。缓存不能替代岗位台账。
- AI网络失败会在同一个 flushEvaluations 中持续等待重试，缺少将异常批次移到持久队列后继续其他可处理任务的调度。模型错误格式又直接 outputReview，把协议问题转给用户。
- 休息按累计业务动作触发，动作包括选详情、来源、列表、反馈、提交。100个业务动作不等于100个岗位；完整吞吐量必须包含休息、AI等待和重复读取时间。人工节奏记录也不能证明平台不会限制账号。
- 登录、业务队列、网页状态和旧停止记录耦合。近期 Cookie 已有但页面未进入职位页的死锁说明：只测单个接口正常不够，必须覆盖扫码后、关闭后、重启后和旧记录恢复的完整路径。
- 黑名单既包含明确排除记忆，也可能残留旧错误规则产生的记录；记录没有判定规则版本，规则修正后历史误排除未必自然纠正。需要可追溯依据与重评入口，不能擅自清空用户排除。
- 职责清晰度、行业、语言和工时存在本地启发式与语义规则。应评估误拒/误放和无法判断率；不能仅通过几个定制正例测试就宣布可靠。
- 运行日志主要在内存，任务状态主要持久化日配额。发生重启或用户报错时，缺少统一的逐岗位事件轨迹。“已开聊”也不是已附上简历、已回复或已获面试。

## 5. 还缺哪些真正的求职功能

官方产品研究见 job-search-feature-research-2026-10-12.md。

Huntr 将保存、申请、面试、Offer及回复时间纳入漏斗；Teal 将完整JD、联系人、跟进、简历版本及面试轮次归到岗位台账。这些是流程参照，不证明其能同步BOSS，也不证明BOSS提供可用消息API。

1. **持久岗位台账与发送对账**：搜索、判断、开聊、附件、回复、面试都有明确状态；结果不明先核对，跨天和重启不重复发送。
2. **条件询问—回复—证据更新**：在用户授权的策略下询问未写明条件，按对方实际回复更新工时/休息/资格证据，不把AI推断当作招聘方承诺。
3. **招聘方回复收件箱与下一步**：把要简历、补作品、回答问题、面试邀请和拒绝整理成待办；没有验证接入能力前不承诺自动读取或发送。
4. **跟进和机会归档**：控制重复联系，知道哪些机会值得跟进、哪些已结束，停止在没有回复的公司上反复浪费时间。
5. **面试管理与岗位准备包**：岗位JD、公司资料、关键条件、面试时间和轮次聚合，给出准备要点与应问问题。
6. **Offer与实际条件对照**：固定薪资/绩效、试用期、工时、轮班、地点、合同主体与招聘承诺对照，未知项明确保留。
7. **简历/作品与附件版本管理**：先把“哪个版本用于哪个岗位、是否真正提交”记录准确。原版PDF优化仍未实现，应放在主链路稳定之后验证，不能凭实验代码当完成。

## 6. 应重新建立的主流程

搜索方案 → 发现新增唯一岗位 → 保存资料快照 → 廉价规则处理 → 必要的公司/岗位证据补全 → 本地判定或批量AI → 可执行候选 → 投递/询问确认 → 回复与条件更新 → 跟进/面试/归档。

技术恢复队列贯穿这条链路，拥有自动重读、结果补读和重评责任。人工队列只承担系统无法代替的决定。最终关注真实机会与人工负担，不以候选存量、日志条数或单次评分证明成功。

## 7. 改造次序与验收

### P0：停止把内部失败转嫁给用户

- 岗位链接与持久身份脱离 locator；快照、配置版本、决策与处理状态可恢复。
- 自动重读、资料变化重评、AI协议恢复与人工决策分别建状态。
- 整理已有200条队列：先重读/重评技术问题，再按当前条件计算；保留历史与可追溯结果，不自动删除或投递。
- 统一漏斗与逐岗位原因码，排除重复尝试造成的计数膨胀。

### P1：让搜索和条件策略真正帮助自动化

- 根据新增率和后续收益切换搜索方案；低收益停止当前来源，不偷偷放宽硬约束。
- 明确未知条件允许何种后续动作，按既定授权持续推进。
- 局部资料变化只重算相关部分，减轻公司重开和AI重复调用。
- 建立条件询问、回复和发送对账闭环。

### P2：求职后半流程

回复待办、跟进、面试和Offer对照；之后完成简历版本与原版PDF优化、安装分发和更新机制。

### 验收应如何改变

- 人工池不再因为“列表变了”“需要重新评估”“AI格式错误”新增待办。
- 列表重排、跨休息、关闭重开和同批次评估之后，每个已通过岗位都能继续处理或给出真实不可用原因。
- 相同唯一岗位跨来源/跨轮/跨重启只计一次新增；已发送和发送结果不明不会盲目重发。
- 关闭一个条件后，受影响候选会重算，不再用旧条件继续要求用户确认。
- 高分与条件未知分开呈现；用户可以解释为什么未投，而不必从日志猜测。
- 用同一批有人工参考判断的岗位做前后对照，记录误拒、误放、自动推进、技术失败和人工分钟数。没有完整标注就不宣布精确率。
- 实际测试报告必须包含唯一候选、开聊确认、回复和面试；是否出现平台限制与业务收益分别报告，不能用一次未出现限制证明策略有效。

本轮没有运行这些新验收，也没有提出未经测量的通过率承诺。

## 8. 对此前工作方法的反思

我此前经常围绕当次报错修补，再凭构建和局部测试通过给出“已修复”。它验证了某个分支，却没有验证候选从搜索到结果的完整推进。

待确认池被反复用作安全兜底，但没有给系统自己的恢复责任。每增加一种保留规则，就增加用户的操作，而没有衡量人工耗时。AI批量化、公司页核查和浏览节奏分别被改动，也没有持续验证它们组合后的候选流失。

接下来应按漏斗损失、失败责任与真实求职结果组织工作：先建立可复现的历史样本和指标，再修候选流失；明确条件策略后补沟通闭环。只改提示词、分数和停顿，仍会重复现在的问题。
