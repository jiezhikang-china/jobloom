# 待确认岗位投递复核（2026-10-07）

## 现场原因

用户选择 45 个待确认岗位后，第二个岗位点击沟通，流程立即误报“发送结果未确认”并中断。原岗位页面仍打开，按钮已变为“继续沟通”，独立岗位页的 `.startchat-dialog` 中存在 `.message-list .message-item .status.success`，可见文字为“已发送”，同时保留空白消息输入框。

旧代码仅识别标题为“已向 BOSS 发送消息”的另一种确认弹窗，把实际沟通窗口中的空白输入框当作首次招呼编辑框；其发送控件是 `div.send-message`，不是旧选择器中的 `button`，因此提前返回未知结果。

## 修改

- 同时支持列表确认弹窗和独立岗位页沟通窗口。后者须核对当前岗位、可见“已发送”状态和非空消息正文。
- 独立岗位页已打开实际沟通窗口时直接确认成功，不再向空白输入框填入或补发第二条消息。
- “发送中”、其他岗位的历史消息不能作为成功证据；真正无法确认的发送仍中止批次，避免重复投递。
- 岗位标题先渲染时继续等职位描述；详情、公司页、关键筛选字段或沟通入口读取失败发生在提交前时，保留该条并继续后续岗位。
- 已沟通记录优先去重，不再因无关筛选字段缺失而阻断批次。
- 账号限制、验证、条件变更及提交后的未知结果仍停止整批。

## 验证

- `review-chat-dom.test.ts`：真实 Chrome CDP + 本地拦截页面，覆盖异步描述、立即及延迟发送确认、不二次填入/发送、目标变化、发送中不误报成功。
- `delivery-review.test.ts`：单条/批量入口、排除条件、距离、配额、去重、继续失败防重复；新增多条详情失败后继续有效岗位、已沟通但字段缺失、验证中止。
- `dom-batch.test.ts`：保留原列表页面的发送、确认弹窗和“继续沟通”行为。
- 前后端构建、桌面启动回归、待确认界面测试。

现场只读取原来已发送岗位的状态用于核对漏计，没有重新向招聘方发送消息。

经新版 CDP 读取逻辑核实，原岗位确已发送。先备份原配额和待确认列表，再补回 1 次漏计：今日累计由 1 改为 2，仅移除这条已发送记录，其余 44 条保留。修复版后台为 28，桌面已重启，BOSS 登录保持有效。
